# P14 — Data dictionary + known quirks

## The orders file — `data/raw/orders_SAMPLE.csv`

SAMPLE orders file for the fictional shop **SastaBazaar, Lahore**,
Jan–Dec 2025. 1,598 orders from 500 customers, PKR 11,633,750 total.
Generated by `src/generate_data.py` (seed 20261110) with customers
built in archetypes (Champions, Loyal, regulars, one-time buyers,
lapsed, new) so the RFM spread is realistic. Snapshot date for
recency is 2025-12-31.

| Column | Type | Meaning |
|---|---|---|
| order_id | text | `SB-10001` … `SB-11598`; the file's key — must be unique |
| order_date | text | ISO `YYYY-MM-DD`; the file covers Jan–Dec 2025 |
| customer_id | text | `SB-C0001` … `SB-C0500`; one id per customer |
| customer_name | text | Customer's name |
| customer_email | text | Placeholder `@example.com` address — never a real email |
| product_code | text | Must exist in the product master (41 products) |
| product_name | text | Product name as written on the order |
| category | text | Product category (Grocery, Electronics, Home & Kitchen, Clothing, Stationery, Personal Care) |
| quantity | integer | Must be > 0 |
| unit_price | integer (PKR) | Must be > 0 |
| total_amount | integer (PKR) | Must equal quantity × unit_price |
| payment_method | text | One of: Cash on Delivery, Bank Transfer, JazzCash, Easypaisa, Card |
| city | text | Delivery city (Lahore, Karachi, Islamabad, Rawalpindi, Faisalabad, Multan) |

## The RFM scores — `data/processed/rfm_scores.csv`

One row per customer (500 rows), computed by `src/rfm.py`:

| Column | Type | Meaning |
|---|---|---|
| customer_id … city | — | Same as the orders file (first order's values) |
| first_order / last_order | text | ISO dates of the customer's first / last order in 2025 |
| recency_days | integer | Days from last order to 2025-12-31 (0 = bought on the last day) |
| frequency | integer | Orders in 2025 |
| monetary | integer (PKR) | Total spend in 2025 |
| avg_order_value | integer (PKR) | monetary / frequency |
| r_score / f_score / m_score | integer 1–5 | Quintile scores (ntile; each holds ~20% of customers). R is reversed: most recent = 5 |
| rfm_score | integer | R×100 + F×10 + M (e.g. 555 = top on all three) |
| segment | text | One of the 7 segments (see the segment map in the README) |

## The segment summary — `outputs/segment_summary.json`

Machine-readable summary: headline KPIs, one row per segment
(customers, share, orders, revenue, share of revenue, averages) and
the score counts per quintile.

## The database — `data/processed/rfm.db`

SQLite, star-lite: `dim_customer` (500 rows, with R/F/M + segment),
`fact_orders` (1,598 rows), `dim_product` (41 products). Rebuildable
from the pushed scripts and CSVs (`python3 src/build_sqlite.py`) and
intentionally NOT uploaded to GitHub.

## Known quirks (kept, flagged, never silently edited)

- **40% of customers bought once** (200 of 500) — the shop's real
  shape, not a data error. F scores 1 and 2 are both mostly one-time
  buyers because of it.
- **Quintiles are relative.** A score of 5 means "top 20% of this
  file", not an absolute threshold. The same behaviour scores
  differently on a different file — compare segments within one run.
- **Ties inside a quintile are split by customer_id.** Two customers
  with the same frequency can land in different F scores; the
  generator shuffles archetypes before assigning ids so the split is
  neutral (see `src/rfm.py`).
- The product master has 41 products across 6 categories; the most
  common payment is Cash on Delivery. Cities are Lahore, Karachi,
  Islamabad, Rawalpindi, Faisalabad, Multan.
- `data/processed/rfm.db` is rebuildable from the pushed scripts
  and CSVs (`python3 src/build_sqlite.py`) and is intentionally NOT
  uploaded to GitHub.
